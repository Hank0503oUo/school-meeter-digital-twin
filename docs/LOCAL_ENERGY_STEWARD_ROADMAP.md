# 本地能源管家：終局目標與後續施工指引

本文件供之後繼續實作時對齊方向：**只使用本地小模型**作為對話與編排核心，**數值正確性與預測**由底層工具與儀表保證。

**目前部署的對話模型**：**Gemma 4 E2B**（LM Studio 等本機推論）。官方規格與最佳做法見 [Gemma 4 模型資訊卡](https://ai.google.dev/gemma/docs/core/model_card_4?hl=zh-tw)。與本架構的對齊說明見 **§12 附錄**。

**產品目標對齊**：以 **E2B 為預設**，讓能源管家能在 **一般文書／工作筆電** 上 **盡量無腦使用**（雙擊啟動、少設定、本機可跑）；知識靠 **RAG**，數字靠 **工具／儀表**，必要時再以 Colab／工作站做 LoRA，**不**把大模型當日常門檻。

---

## 1. 終局目標（一句話）

本地小模型負責 **呼叫工具、理解上下文、把工具／儀表結果說清楚**；**PI-VD／統計／儀表數字**不應由模型「心算」產生。

## 2. 四項能力與建議作法

### 2.1 會呼叫工具，並接到底層預測模型

| 作法 | 說明 |
|------|------|
| 少數穩定工具 | MCP 工具數量克制、schema 清楚；避免小模型在過多工具間迷路。 |
| 強型別與必填欄位 | 參數錯誤由後端回饋可讀錯誤，必要時 **後端補齊**（例如天氣序列、預設時數）。 |
| 迭代上限 | 限制 `ENERGY_LOCAL_MCP_MAX_ITERATIONS` 等，避免無限循環。 |
| 預測在引擎內 | `run_pvid` 等走 `AlgorithmMCPBackend`／PIVDEngine；模型只決定「算什麼、用哪個 uid／時間窗」。 |

**相關程式（可延伸）**：`src/lm_studio_client.py`、`src/demo_mcp_server.py`、`src/algorithm_mcp_backend.py`、`src/dashboard_modules/assistant_views.py`（本地 agent prompt）。

## 5. 建議施工順序（優先級）

**已定調：先走 RAG**——用大模型建圖／蒸餾可之後再說；Gemma 2B 先靠 **檢索到的 chunk + 儀表／工具數字** 回答。

1. **文件 RAG 管線**（Workbench／chunk／metadata、檢索再接進助理或 MCP `search_knowledge` 類工具）。  
2. **儀表 snapshot + 少數 MCP 工具** 穩定（含 `run_pvid` 與統計類）；**數字仍以工具為準，RAG 只補脈絡**。  
3. **工具輸出 → 固定摘要範本**（小模型專心「說人話」）。  
4. **領域詞彙表**（別名 → 正式 id，與 RAG 並行補強）。  
5. **評測集**（固定問題集 + 預期引用來源／工具），再考慮 **graphify 全圖** 或 **LoRA／蒸餾**。

## 8. 擴充多個 RAG 庫（ESG 碳管理、綠建築法規）

之後若要**另外**掛 **ESG／碳管理** 與 **綠建築法規** 兩類知識，建議從「資料分區 → 檢索策略 → 產品責任」三層施工，避免與既有能源儀表 RAG 糊成一團。

### 8.1 資料分區（強烈建議）

| 作法 | 說明 |
|------|------|
| **物理分庫／分目錄** | 例如 `corpus/esg_carbon/`、`corpus/green_building_codes/`（名稱自訂），匯入 Workbench 或索引管線時帶 **固定 collection／tag**。 |
| **metadata 必打** | 每個 chunk 至少：`kb`（如 `esg_carbon` \| `green_reg`）、`doc_id`、`effective_date` 或 `version`（法規特別重要）、`locale`（中／英／地方法規）。 |
| **法規庫版本** | 法條會改；檢索結果要能顯示「依據哪一版／哪一條」，必要時 **人工公告更新日** 寫在 UI 或回答模板。 |

### 8.2 檢索要怎麼接進助理（三種模式，可並存）

| 模式 | 適用 | 作法摘要 |
|------|------|----------|
| **合併檢索** | 問題可能跨域 | 單次向量／關鍵字搜多庫，結果依 score 合併，但 **回答時必須標註來源庫**（`esg` vs `reg` vs `campus_energy`）。 |
| **路由檢索** | 問題類型分明 | 先用規則或小分類器判斷意圖（碳盤查 vs 法規 vs 儀表），**只查對應庫**，較省噪音。 |
| **混合** | 量產系統 | 儀表／工具優先；**補 RAG** 僅用於定義、流程、法條解讀；數字仍以工具與申報系統為準。 |

實作上可演進為：**一個 MCP 工具** `search_knowledge(query, collections=[...])`，或在既有分析管線裡依 `task_type` 掛不同 `collection` 列表。

### 8.3 ESG／碳管理特別注意

- **排放數據、係數、邊界** 若會影響申報或決策，**優先接表單／計算工具或官方係數庫**，RAG 只補 **方法論、名詞、流程**。
- 在 prompt 或 UI 固定一句：**碳相關數字須引用標註來源（工具／表單／係數版本），不得僅憑文件片段推斷。**

### 8.4 綠建築法規特別注意

- **法律免責**：助理輸出宜標示「僅供參考，正式適用請以主管機關與最新公告為準」。
- **地域**：中央／地方／版本差異大，metadata 與路由（見 8.2）比「一個大雜燴向量庫」重要。
- **與能源雙生的關係**：法規庫多用於 **對照設計條件、名詞、申請流程**；**實際能耗與預測**仍回儀表與 PI-VD。

### 8.5 與本文件第 2 節的關係

- **§2.2 詞語關聯**：兩庫會大幅增加同義與專有名詞，可為 ESG／法規各做 **小型別名表**（或從 chunk 自動抽，再人工審）。
- **§2.3 儀表數據**：不變——**RAG 不取代儀表**；法規／ESG 是「脈絡與合規視角」 layer。
- **§5 施工順序**：建議在「儀表 + 工具穩定」之後，再 **分庫上線** ESG 與法規，並各做 **小型評測題組**（避免法條幻覺）。

## 9. 法規門檻 × 數值情境 × 節能計畫（如何結合並調動工具優化）

目標：從 **法條** 得到「不可超過多少」、從 **雙生／預測工具** 得到「現在這樣開會多少」，再產出 **節能計畫** 並 **反覆用工具試算** 直到情境在門檻內或說清楚取捨。**法條不負責算 800 kW；工具才算。**

### 9.1 三層資料（不要混成一坨文字）

| 層級 | 應來自 | 例（你題目中的敘述） |
|------|--------|----------------------|
| **約束 Constraint** | RAG＋**結構化**（或合規資料庫／人工表） | `max_demand_kw = 500`、適用範圍（單棟／校區）、條文引用與版本 |
| **狀態 State** | 儀表 snapshot、**`run_pvid`／情境試算** | 「此建築群、此情境下**高峰需量 800 kW**」必須是 **工具回傳欄位** |
| **操縱變數 Levers** | 你系統已定義的節能手段 | 冷卻水溫、冰機台數、排程、設定溫度、照明／設備比例等 → 對應到既有 **slider／scenario 參數** |

法條經 RAG 讀出後，理想上要能 **落成 JSON／表列**（例如 `constraint_type=max_peak_kw`, `value=500`, `source_chunk_id=...`）。若抽取不可靠，**第一階段用人工維護「建物／校區合規門檻表」**，RAG 只負責展示條文出處。

### 9.2 範例流程：500 kW 上限 vs 800 kW 情境

1. **取得約束**：`max_kw = 500`（附法源與版本）。  
2. **取得基準或假設情境需量**：呼叫工具（例如全開冷氣、某典型日）→ 得到 `peak_kw = 800`。  
3. **缺口由程式算**：`gap_kw = 800 - 500 = 300`（寫進給模型的上下文，避免模型自己減錯）。  
4. **節能計畫（模板）**：  
   - 目標：高峰需量 ≤ 500 kW；  
   - 現況：800 kW；缺口 300 kW；  
   - 可行手段：對應你系統裡 **每個 lever 能動什麼**；  
   - **每一步都再 call 工具**：改一組參數 → 讀回新的 `peak_kw`／能耗。  
5. **「最佳化」**：  
   - **A. 模型驅動**：小模型依序提案 2～3 組情境（保守／積極），每組 **工具驗證**；  
   - **B. 程式驅動（較穩）**：後端對 lever 做 **網格搜尋／簡化優化**，在 `peak_kw ≤ 500` 下找成本最低或舒適度折衷；模型只負責 **解釋表格與取捨**。  
   實務上 **B 保證可行解**，**A 補敘事與排序建議**。

### 9.3 「學會列計畫」在工程上代表什麼

- **不是**把法條與數字混進去 **end-to-end 訓練** 一顆小模型就算學會。  
- **而是**：固定 **Planner prompt**（目標、約束、缺口、可用 lever 列表）＋ **強制工具呼叫** ＋ **可選 few-shot**（一兩份「好的節能計畫」範例）。  
- 模型學的是 **格式與推理步驟**，**數字可信度** 永遠來自工具。

### 9.4 建議補齊的後端／MCP 能力（可漸進）

| 能力 | 用途 |
|------|------|
| `get_constraints(scope)` 或合規快取 | 回傳結構化門檻，減少純 RAG 幻覺 |
| `evaluate_scenario(uid, scenario)` | 回傳 `peak_kw`、能耗、必要時分項 |
| （可選）`optimize_under_constraint(max_kw, levers)` | 程式搜尋可行解，LLM 解讀 |

與既有儀表連結：**snapshot 提供「現在」**；**`run_pvid`／情境試算提供「若怎樣做會變多少」**；法規層只提供 **不等式約束**。

## 10. 建築群、多限制與「整體最佳化」——要不要獨立一支最佳化／排程工具？

### 10.1 先釐清：誰在「學會」？

- **小模型不適合**在腦內做 **多建物、多約束、全域 min／max** 的數學最佳化；容易看似合理、實則不可行或違反限制。  
- **合理分工**：  
  - **最佳化引擎**（你另寫的程式）：輸入「建物列表、狀態、可操作變數上下界、目標函數、硬限制」→ 輸出「分配／排程／建議 lever 向量」。  
  - **小模型**：把使用者話語 **對齊成結構化輸入**、讀 **工具回傳**、用 **人話解釋**取捨與風險。  
- 「學會」在產品上 = **固定流程 + 好工具 + few-shot 範例**，不是指望模型自己發明演算法。

### 10.2 為什麼值得做「單獨一支」`optimize_campus`／`schedule_loads` 類工具？

| 理由 | 說明 |
|------|------|
| **可驗證** | 同一組輸入得到可重現輸出，方便與儀表／法規對帳。 |
| **可測** | 單元測試約束是否被滿足（例如校區總尖峰 ≤ 門檻、單棟下限）。 |
| **可換心** | 第一版用 **啟發式／網格／線性近似**，之後換 OR-Tools、MILP 不改對話介面。 |

建議在 MCP 上暴露 **一個（或一小組）明確介面**，例如：

- `optimize_energy_allocation`：輸入 `building_ids[]`、`per_building_levers` 邊界、`global_constraints`（尖峰、總電量、法規門檻）、`objective`（例如最小總能耗、或最小尖峰、加權）；輸出 **每棟建議設定** + **指標**（總 kW、分項）。  
- 內部可 **反覆呼叫** 既有 `evaluate_scenario`／`run_pvid` 當 **oracle**（黑箱評估），外面用搜尋器找較佳解。

### 10.3 整體最佳化的常見形狀（由簡入繁）

1. **單一時間切片**：只優化「下一時段」或「典型日高峰」的負載分配（較易）。  
2. **多時段排程**：每棟 **時段曲線** 或 **開機順序**，變數變多 → 需要較正式的 **排程 / 滾動最佳化**。  
3. **與法規／ESG 合併**：把 `max_kw`、`碳上限` 等當 **硬限制或懲罰項** 寫進目標函數，**數值來自 §9 的約束表**，不是 RAG 原文。

### 10.4 與助理的串接方式

1. 使用者：「在校區總尖峰不超過 X 的前提下，盡量降某幾棟的能耗。」  
2. 模型解析 → 呼叫 **`get_constraints`**（或讀快取）+ **`get_building_states`**（snapshot）。  
3. 組成 **`optimize_*` 的 JSON 參數**（可由 schema 強制檢查）。  
4. 工具回傳 **表格化方案** → 模型 **摘要、對照限制、標註不確定性**（例如模型假設、天氣情境）。  

### 10.5 小結

- **是，建議做獨立的最佳化／排程工具**（或至少一個 **MCP 封裝層** 呼叫你現有的 Python 最佳化模組），讓「整體最佳化」成為 **可呼叫、可測、可換演算法** 的能力。  
- 小模型負責 **意圖 → 參數** 與 **結果 → 人話**；**全域最優或可行解** 由程式算。

### 10.6 物理引擎：直接用 PI-VD（`run_pvid`）還是呼叫 EnergyPlus？

兩者都可以當 **「給定操作與邊界 → 回傳負載／能耗」的評估器**，再被 **最佳化外層** 反覆呼叫；差別在 **速度、細節、整合成本**。

| 後端 | 適合當最佳化內圈？ | 說明 |
|------|-------------------|------|
| **PI-VD（本 repo 已接 `run_pvid`）** | **是，首選做迭代** | 與現有 MCP／天氣補齊已對齊；單次評估相對輕，適合 **大量試算**（網格搜尋、啟發式）。 |
| **EnergyPlus** | **可以，但通常不拿來當唯一內圈** | 模擬較重（IDF／EPW、執行時間）；較適合 **離線校準**、**最終方案抽樣驗證**、或 **少量點** 的精算。 |

**建議形狀**：

- **日常最佳化／助理對話**：外層 `optimize_*` **反覆呼叫 PI-VD**（或現有 `evaluate_scenario`）當 oracle。  
- **要對標法規或細部物理**：可 **選配** `run_energyplus_scenario` 類 MCP（子程序跑 EP、解析 SQL/CSV 輸出），僅在 **少數候選解** 上跑，避免對話卡死。  
- **混合**：先用 PI-VD 收斂到幾組可行解，再用 EnergyPlus **抽驗** 1～3 組。

技術上 EnergyPlus 需處理：**IDF 版本、天氣檔、執行時間、錯誤日誌**；都適合封在 **單一 MCP 工具** 裡，對模型仍是一個「評估黑箱」。

## 11. 補漏 Review：你還沒覆蓋到的能源管家功能

以下是對照能源管理實務盤點後，目前路標 **尚未提及** 但實際上線時大概率會碰到的事項。

### 11.1 主動異常偵測與告警

目前助理是「人問才答」；但能源管家更常見的價值是 **主動說**：

- 某棟近日尖峰異常上升。
- 某電表掉線／數據斷裂。
- 週末負載不降反升（疑非必要負載）。

**做法**：定期或事件驅動的 **後端檢查規則**（程式寫、不靠 LLM），觸發後再 **推給對話層** 用自然語言描述；或在儀表板加「通知列」。

### 11.2 天氣預報（前瞻，非只有歷史）

目前天氣主要是 **EPW／歷史序列**；若要做節能「排程」或「明天的建議」，需接 **短期氣象預報** API（或 TMY 做近似）。

- 預報接好後，`run_pvid` 與最佳化都可以改為 **前瞻模式**。
- 對話時模型可以說：「明天預測高溫 36°C，建議提前降載。」

### 11.3 電費結構與需量計費（Demand Charge / TOU）

能源管家若不知道 **電價費率**，省下的 kWh 無法換算為 **省下的錢**。

- 時間電價（TOU）、尖峰需量計費、契約容量（超約罰款）等，最好有 **結構化費率表** 供工具查詢。
- 最佳化目標可能不只是「min kWh」而是「min 電費」或「不超過契約容量」。

### 11.4 排程與行事曆感知

- 校園有 **學期 vs 寒暑假 vs 考試週 vs 國定假日**，負載模式差異很大。
- 若助理不知道「今天是暑假」，給出的對照或建議會錯。
- 做法：維護 **校園行事曆 JSON**，snapshot 或 prompt 裡標「目前為學期中 / 假日」。

### 11.5 電表資料品質與缺值處理

- 電表可能 **斷線、回補、出現異常跳躍**。
- 助理應知道「這段期間資料不完整」；工具結果附 **coverage_ratio** 或 **missing 標記**。
- 避免在資料缺失時仍信心滿滿做結論。

### 11.6 故障診斷（FDD, Fault Detection & Diagnostics）

- 比「異常偵測」更深一層：不只說「能耗高了」，而是推理 **原因**（冰機 COP 劣化、空調箱外氣閥卡住、照明排程未關等）。
- 初期可用 **規則型 FDD**（閾值 + 條件判斷）；進階可接 **ASHRAE Guideline 36** 等標準。
- 助理角色：把 FDD 的 **結構化 fault code** 翻譯成人類可讀、附建議工單。

### 11.7 定期報表與匯出

- 校園管理者要 **月報、季報、年度能效報告**（可能含法規要求格式）。
- 助理可觸發「報表產生」工具，輸出 PDF / Excel / Markdown，而不是只能在對話框看結果。
- 也可與 **ESG 申報** 對齊（§8）。

### 11.8 多角色與權限

不同使用者關心不同事：

| 角色 | 關心 |
|------|------|
| 設施主管 | 異常、月帳單、契約容量 |
| 能源工程師 | 情境試算、FDD、冰機效率 |
| 校級主管 | KPI 摘要、ESG 進度、法規合規 |

初期可用 **task_type** 或 prompt 切換語氣與深度；長期考慮 **角色分流**。

### 11.9 人類回饋迴圈（Correction → 改進）

- 人類說「這建議不對」或「上次算的結果後來驗證偏差很大」時，如何 **回灌**？
- 短期：存 curated trace、標「rejected / corrected」、之後 prompt 或 RAG 可引用。
- 長期：累積足夠 **（問題, 正確答法）** 對後再考慮 LoRA。

### 11.10 安全與離線韌性

- 本地模型的優勢就是 **不出外網**；但要確保 **API key 不外洩**（尤其若同時有 cloud toggle）。
- 網路斷線時助理與工具仍應 **可用**（純本地路徑），儀表資料若有快取即可。

### 11.11 與 BAS / BMS 的對接（長期）

- 若最終要從「建議」變成「執行」（例如自動調溫、排程寫回控制器），需要 **BACnet / Modbus / IoT gateway** 整合層。
- 助理角色會從「顧問」升級為「操作員介面」——需更嚴格的 **確認流程** 與 **安全機制**。
- 初期先做好「只建議、不控制」的邊界即可。

## 12. 附錄：Gemma 4 E2B 與能源管家架構

本專案以 **Gemma 4 E2B** 作為本地助理後端時，與 §1～§2 的設計 **一致**：小模型做 **編排與說明**，**PI-VD／儀表／MCP** 負責數值與物理。

### 12.1 與官方規格相關的實務重點（摘要）

| 項目 | 對能源管家的意義 |
|------|------------------|
| **約 2.3B 有效參數（PLE／含嵌入表較大）** | 適合筆電／工作站本機；仍應 **少工具、清楚 schema、迭代上限**（§2.1）。 |
| **128k 脈絡長度** | 有利於長文件 RAG／多輪附帶 snapshot；仍建議 **先檢索再塞入**，避免整本貼進 prompt。 |
| **文字、圖片、音訊（E2B）** | 除對話外，日後可選：儀表截圖／曲線圖解讀、簡短語音指令（需管線支援，非必做）。 |
| **原生函式呼叫、system 角色** | 與 MCP／OpenAI 相容工具流程契合；請在 LM Studio 端確認 **tool 格式** 與模型版本一致。 |

詳細層數、滑動視窗、取樣建議等以 [官方模型卡](https://ai.google.dev/gemma/docs/core/model_card_4?hl=zh-tw) 為準。

### 12.2 能力邊界（誠實對齊）

- 官方基準裡，**較小模型在長鏈代理、超難推理**上弱於 31B／MoE 變體；因此 **§9～§10** 的「約束＋程式最佳化／反覆試算」比「全靠模型心算」更可靠。  
- **事實與法條**：仍以 **RAG＋出處** 與 **合規表** 為準，不單依模型記憶（§8、§9）。

### 12.3 環境變數提醒

本 repo 本地助理預設以 **OpenAI 相容 API**（如 LM Studio）連線；請設定 `ENERGY_LOCAL_LLM_BASE_URL`、`ENERGY_LOCAL_LLM_MODEL`（或自動偵測）指向已載入的 **Gemma 4 E2B** 模型名稱。

### 12.4 天氣／電力「線圖」要不要給模型看？（視覺 vs 數值）

**預設建議：不必。** 讓 **PI-VD／儀表／預測管線** 吃 **時間序列數值**（EPW、CSV、儀表 API）即可；這是 **可重現、可驗證** 的主路徑。

| 做法 | 何時適用 |
|------|----------|
| **只餵數值給底層** | 常態：天氣、負載、需量已經在系統裡；`run_pvid`、統計、最佳化都應以 **陣列／表格** 為準。 |
| **多模態「看線圖」**（Gemma E2B 可選） | **例外**：僅有 **截圖／掃描報表**、無 API；或使用者 **貼圖** 問「這張圖在說什麼」——此時視覺是 **輔助輸入**，讀出後仍應 **轉成數值** 再進引擎，或明確標註「圖讀值不精，僅供說明」。 |

**風險**：從軸線、刻度、圖例 **視覺讀數** 會有誤差，與能源管家的 **審計需求** 相衝。因此 **圖→解釋** 可以，**圖→當作真實輸入進 PI-VD** 不建議。

**若要做 UX**：用線圖做 **儀表板展示**；助理回答時引用 **同一套後端數值**（或工具摘要），圖只是幫人類對齊直覺，不必讓模型「看圖算物理」。

### 12.5 官方文件重點摘要（與 LM Studio 部署對照）

以下整理自 [Gemma 4 核心說明／模型卡](https://ai.google.dev/gemma/docs/core/model_card_4?hl=zh-tw) 與官方「最佳做法」；**本 repo 實際走 OpenAI 相容 API（LM Studio）**，若與下列 Transformers 範例不完全一致，以 **LM Studio 可設定的參數** 為準。

| 主題 | 官方建議 | 能源管家實務 |
|------|----------|----------------|
| **取樣** | `temperature=1.0`、`top_p=0.95`、`top_k=64` | 工具編排要穩時，可在 LM Studio **略降 temperature** 試驗；以 **不重複亂 call 工具** 為準。 |
| **思考模式（thinking）** | `enable_thinking=True` 或 system 前加 `<|think|>`；多輪時 **歷史只保留最終回覆、不含思考內容** | 複雜推理可開；**MCP 多輪**時注意 **延遲與 token**；務必遵守「不把 thought 寫進下一輪 user 上下文」。 |
| **多模態順序** | **先圖／音訊，再文字** | 若未來做截圖問答，提示組裝時遵守順序。 |
| **圖像權杖預算** | 70／140／280／560／1120 | OCR、小字、文件用 **較高**；分類／快篩用 **較低**（省算力）。 |
| **音訊／影片長度** | 音訊約 **30 秒** 上限；影片假設約 **每秒一影格** 時長約 **60 秒** | 語音下指令可當 **短指令**；長簡報需分段。 |
| **函式呼叫** | 原生支援結構化工具 | 與 **MCP／`chat_with_mcp`** 路線一致；仍宜 **少工具、強 schema**（§2.1）。 |

**部署差異**：官方範例用 `transformers` + `AutoProcessor` 直接載入 `google/gemma-4-E2B-it`；你方若只用 **LM Studio 推論**，不一定能一一對應 `enable_thinking`、`parse_response`、多模態 processor，需以 **LM Studio 該版本支援的 Gemma 4 能力** 為準。
